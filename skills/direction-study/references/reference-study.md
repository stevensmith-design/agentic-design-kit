# Reference study — extract a visual language, then adapt it

Open the actual originals and keep them visible during synthesis and proof-building. Study each
source separately before considering combinations. Keep **3–5 concrete observed defining traits**
per source as a short summary, backed by the provisional visual guide below. Generic taste words
or a palette alone do not describe the source's visual character.

## Extract a provisional visual guide per source

Use `templates/reference-visual-guide.md` alongside each original. Cover the visible axes that
matter; mark missing evidence unknown instead of inventing values or filling every cell:

- **Colour roles and balance:** canvas, surfaces, text, actions, accents and graphics; where each
  appears, its approximate coverage and contrast/saturation relationships. A hue without its role
  is incomplete. Sparse vivid accents on a near-white canvas do not imply a pastel page background.
- **Typography:** display/body/label character, hierarchy, relative scale, weight, width, case,
  line height and measure. Verify font names from inspectable source declarations when available;
  otherwise describe visible characteristics and label any proposed substitute as an adaptation.
- **Layout and rhythm:** alignment, grid, density, whitespace, spacing relationships and reading
  order. Separate reusable relationships from the source's exact hero and section sequence.
- **Components and surfaces:** shape, borders, fills, elevation, controls and recurring treatments.
- **Images and graphics:** medium, subject, crop, placement, prominence and relation to text. A
  screenshot does not establish motion, hidden states or responsive behaviour; record those unknowns.

Separate **observed**, **estimated**, and **proposed** choices. Keep exact values only when measured
or verifiable, and label estimates. The guide is a small working style vocabulary, not production
`DESIGN.md`, a token-validation exercise or a replacement for the original. Do not invoke
`ui-design-system` Extract (existing application code) or `brand-to-system` (a compatible declared
brand) merely to study screenshots. After selection, system creation can encode the chosen guide.

## Settle how the person wants to use the examples

Reuse explicit preferences already supplied. Otherwise ask one concrete question, using the visible
examples: **“Do you want to carry over a reference's full visual style, use the examples loosely,
or mix selected ideas? Are these alternatives to choose between?”** Name the sources or show their
thumbnails so the person need not interpret abstract design terms. They may choose a different
influence strength for each direction. Ask about layout recreation separately only if material.

Record the answer and its date. For receipt compatibility, use `rearranged` for faithful style
adaptation to new content or deliberate mixing, `loose` for loose inspiration, and `close` for an
explicit request to recreate a source's layout/design within recorded permission and limits.
Faithful colours, typography and component styling do not by themselves request the same layout.
Do not silently choose loose inspiration or interpret enthusiasm as permission for close recreation.
For mixed influence strengths, record the per-direction choices in the contracts; the receipt's
study-level value describes the overall request, not permission to override those choices.

Then resolve only material unanswered questions, bundled when useful:

- **Reference/rule conflicts:** show concrete observed traits that meet Tier-2 gates and ask which
  to approve, decline or qualify. Record the dated actual answer and transcript locator. If none
  are gated, say so briefly; do not ask for blanket approval of ordinary visual observations.
  Study authority does not waive contrast, legibility, hierarchy, usability or reduced-motion needs.
- **Image dependency:** identify whether the character depends on photography, illustration,
  cutouts, rendered objects or product UI. Reuse known permissions; otherwise ask about supplied
  assets, labelled generated placeholders or proposed study mockups. A type-only reinterpretation
  needs agreement when it changes the character. Ask for content only where it changes the proof.

## Alternative styles versus deliberate combinations

When the person supplies contrasting examples because they are undecided, treat them as alternative
visual languages. Let each direction carry a coherent source style into the actual content; do not
force every example into every direction or create a shared compromise palette first. Do not assume
that three examples always mean three directions: follow the requested count and stated intent.

Mix references when requested or when the relationship is intentional and explained. Name a lead
style and each supporting contribution, check compatibility, and preserve their roles. Do not use
coverage as a reason to add an unrelated font, colour or device. Each supplied reference must lead
or contribute meaningfully somewhere, or have human confirmation before omission. Never average
all sources into every direction. A token colour mention is not meaningful coverage.

## Adapt the system to content; expose departures

Carry the source's visual relationships into this project's hierarchy and function. For example,
a marketing reference can inform a blog's typography, neutral ground, vivid graphic accents and
component treatment without importing its sales hero, pricing grid or section sequence.
Do not copy a layout to compensate for weak extraction. Do not invent a recurring signature device
just to make an option distinctive; new devices need a basis in the content, brief or agreed style.

Check current project requirements and prior accepted/rejected directions before choosing values.
If a requirement (including a numeric colour-distance test) conflicts with the requested style,
state the conflict and show the smallest compatible adaptation. If it materially changes the style,
ask which requirement may change; do not silently override an approved constraint. Label a value
chosen for a project rule as a project-driven departure, never as an observation from the source.
A passing measurement does not establish reference fidelity. An exclusion invented by the builder
cannot cancel a stated preference or make lost character acceptable to review.

Plan imagery per direction: role, source or generation brief, placement, fallback and labels.
If a tool or quota fails, disclose the gap and use an already agreed fallback, or ask before
substituting a different medium, sharing assets or reducing the scope. SVG is appropriate when it
fits the agreed treatment, not an automatic replacement for photography or rendered illustration.
Never claim illustrative mockups, sample content or generated assets as verified product evidence.

Stabilize temporary files when possible and disclose inaccessible sources. Notes and custody
receipts help memory and access, but never substitute for viewing the originals.
